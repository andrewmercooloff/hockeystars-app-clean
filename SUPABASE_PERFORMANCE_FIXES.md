# Инструкция по исправлению проблем производительности в Supabase

## Обзор

Этот скрипт исправляет предупреждения о производительности из Database Linter:

1. **auth_rls_initplan** - Оптимизирует RLS политики, заменяя `auth.uid()` на `(select auth.uid())` для предотвращения переоценки функции для каждой строки
2. **multiple_permissive_policies** - Объединяет дублирующиеся RLS политики
3. **duplicate_index** - Удаляет дублирующиеся индексы

## Что делает скрипт

### 1. Оптимизация RLS политик (auth_rls_initplan)

Заменяет вызовы `auth.uid()` на `(select auth.uid())` в следующих таблицах:
- `teams`
- `items`
- `stats_changes`
- `exercises`
- `teams_extended`
- `tournaments`
- `hockey_shops`
- `player_teams`
- `push_tokens`
- `player_museum`

**Почему это важно:** Без `SELECT` обёртки, `auth.uid()` переоценивается для каждой строки в запросе, что значительно замедляет выполнение запросов на больших таблицах.

### 2. Объединение дублирующихся политик (multiple_permissive_policies)

Удаляет дублирующиеся политики в следующих таблицах:
- **exercises**: Удаляет "Anyone can read active exercises" (дубликат)
- **items**: Удаляет "Players can delete own items" (дубликат "Users can delete their own items")
- **player_museum**: Удаляет "Allow delete museum items" (покрывается "Allow delete for owner and admin")
- **player_teams**: Удаляет "Player teams are viewable by everyone" (дубликат)
- **push_tokens**: Удаляет "Allow insert push tokens", "Allow read own push tokens", "Allow update push tokens" (покрываются "Users can manage own push token")

**Почему это важно:** Множественные разрешающие политики для одной роли и действия замедляют выполнение запросов, так как каждая политика должна быть проверена.

### 3. Удаление дублирующихся индексов (duplicate_index)

Удаляет дублирующийся индекс `idx_activity_log_type` на таблице `activity_log` (если он идентичен `idx_activity_log_activity_type`).

**Почему это важно:** Дублирующиеся индексы занимают лишнее место и замедляют операции INSERT/UPDATE/DELETE.

## Как выполнить скрипт

### Шаг 1: Резервная копия

⚠️ **ВАЖНО:** Перед выполнением скрипта создайте резервную копию базы данных!

1. Откройте Supabase Dashboard: https://supabase.com/dashboard
2. Перейдите в **Database** → **Backups**
3. Нажмите **"Create Backup"** или **"New Backup"**
4. Дождитесь завершения создания резервной копии

### Шаг 2: Выполнение скрипта

1. Откройте Supabase Dashboard
2. Перейдите в **SQL Editor** (или **Database** → **SQL Editor**)
3. Откройте файл `database/fix_performance_rls_policies.sql`
4. Скопируйте весь содержимое файла
5. Вставьте в SQL Editor
6. Нажмите **"Run"** или **"Execute"** (или `Ctrl+Enter` / `Cmd+Enter`)
7. Дождитесь завершения выполнения

### Шаг 3: Проверка результатов

После выполнения скрипт автоматически выведет результаты проверки:

1. **Проверка RLS политик:** Покажет статус каждой политики:
   - ✅ **ИСПРАВЛЕНО** - использует `(select auth.uid())`
   - ⚠️ **ТРЕБУЕТ ИСПРАВЛЕНИЯ** - всё ещё использует `auth.uid()`
   - ℹ️ **НЕ ТРЕБУЕТ ИСПРАВЛЕНИЯ** - не использует `auth.uid()`

2. **Проверка индексов:** Покажет оставшиеся индексы на таблице `activity_log`

### Шаг 4: Проверка в Database Linter

1. Подождите несколько минут (настройки могут применяться с задержкой)
2. Перейдите в **Database** → **Linter** (или **Reports** → **Database Linter**)
3. Проверьте, что предупреждения исчезли:
   - ✅ `auth_rls_initplan` - должно исчезнуть или уменьшиться
   - ✅ `multiple_permissive_policies` - должно исчезнуть или уменьшиться
   - ✅ `duplicate_index` - должно исчезнуть

## Возможные проблемы

### Ошибка: "policy does not exist"

Если вы видите ошибку о том, что политика не существует, это нормально - скрипт использует `DROP POLICY IF EXISTS`, который безопасно игнорирует несуществующие политики.

### Ошибка: "index does not exist"

Аналогично, скрипт использует `DROP INDEX IF EXISTS`, который безопасно игнорирует несуществующие индексы.

### Политики всё ещё показывают предупреждения

Если после выполнения скрипта некоторые политики всё ещё показывают предупреждения:

1. Проверьте, что скрипт выполнился без ошибок
2. Убедитесь, что все политики были пересозданы (проверьте результаты запроса в конце скрипта)
3. Если политика не была исправлена, возможно, она имеет другую структуру - проверьте её вручную в Supabase Dashboard

## Откат изменений

Если что-то пошло не так:

1. Восстановите базу данных из резервной копии:
   - **Database** → **Backups**
   - Выберите нужную резервную копию
   - Нажмите **"Restore"**

2. Или вручную восстановите политики через Supabase Dashboard:
   - **Authentication** → **Policies**
   - Найдите нужную таблицу
   - Восстановите политики вручную
