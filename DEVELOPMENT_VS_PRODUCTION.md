# Разница между Development Build и TestFlight (Production Build)

## Важное различие

**Development build** и **TestFlight (Production build)** - это **РАЗНЫЕ** типы сборок с разной конфигурацией и поведением.

## Development Build

### Характеристики:
- ✅ Использует `expo-dev-client` с hot reload
- ✅ JavaScript код работает через Metro bundler
- ✅ Debug инструменты включены
- ✅ Некоторые нативные модули могут работать через JavaScript bridge
- ✅ Менее оптимизирован для производительности
- ✅ Больше логирования и диагностики

### Как работает:
- JavaScript код загружается динамически через Metro
- Нативные модули могут работать через bridge
- Модули могут быть "лениво" загружены
- Ошибки видны сразу в консоли

## Production Build (TestFlight)

### Характеристики:
- ❌ Нет hot reload и debug инструментов
- ❌ JavaScript код минифицирован и оптимизирован
- ❌ Все нативные модули должны быть правильно скомпилированы
- ❌ Меньше логирования (может быть отключено)
- ✅ Полностью оптимизирован для производительности

### Как работает:
- JavaScript код встроен в нативный билд
- Все нативные модули должны быть скомпилированы в нативный код
- Нет JavaScript bridge для некоторых операций
- Ошибки могут быть скрыты минификацией

## Почему это важно для аудио-радара

### В Development Build:
- `react-native-audio-recorder-player` может работать через JavaScript bridge
- Callback `addRecordBackListener` может работать через bridge
- Metro bundler может правильно обрабатывать импорты
- Ошибки видны в консоли

### В Production Build:
- `react-native-audio-recorder-player` должен быть полностью скомпилирован в нативный код
- Callback должен работать через нативный код (не через bridge)
- Импорты должны быть правильно разрешены на этапе сборки
- Ошибки могут быть скрыты минификацией

## Возможные причины проблемы

### 1. Нативная интеграция не скомпилирована правильно
- Модуль может не быть включен в нативный билд
- Pods могут быть не установлены правильно
- Нативный код может быть не скомпилирован

### 2. Callback не работает в production
- В production callback может работать по-другому
- Может быть оптимизирован компилятором
- Может требовать дополнительной настройки

### 3. Разрешения не применены
- В production разрешения могут работать по-другому
- Info.plist может быть не правильно настроен
- Разрешения могут требовать дополнительной настройки

### 4. Конфигурация сборки
- EAS build может использовать другую конфигурацию
- Нативные зависимости могут быть не включены
- Оптимизации компилятора могут влиять на работу

## Решение: Fallback на expo-av

Fallback на `expo-av` решает проблему, потому что:
- ✅ `expo-av` полностью интегрирован с Expo
- ✅ Работает стабильно в production сборках
- ✅ Не требует дополнительной настройки нативных модулей
- ✅ Использует polling вместо callback (более надежно)

## Проверка проблемы

### Если в development build все работает:
1. **Проверь логи в TestFlight:**
   - Вызывается ли callback?
   - Есть ли ошибки инициализации?
   - Работает ли метеринг?

2. **Проверь нативную интеграцию:**
   ```bash
   cd ios
   pod install
   cd ..
   ```

3. **Проверь конфигурацию сборки:**
   - Правильно ли настроен `eas.json`?
   - Включены ли все нативные зависимости?
   - Правильно ли настроены разрешения?

### Если проблема подтверждена:
- Fallback на `expo-av` автоматически решит проблему
- Система автоматически переключится, если `AudioRecorderPlayer` не работает
- Это более надежное решение для production

## Вывод

**Development build ≠ Production build**

Если что-то работает в development, это не гарантирует работу в production. Fallback на `expo-av` обеспечивает надежную работу в обоих случаях.
